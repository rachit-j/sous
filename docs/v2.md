# Sous V2 specification

## Approved direction

Serve a few trusted users on one private instance. Build the shared Flask JSON API and responsive web client first. User has no paid Apple developer account and explicitly deferred TestFlight/native iOS work; retain reusable API boundaries for a future client without scheduling that work. Keep Docker Compose. Each user supplies their own AWS connection; never use another user's connection or shared environment AWS credentials. Accounts, recipes, cooking state and credentials are server-authorized independently of the UI.

## Capabilities and delivery order

1. Identity and isolation: username/password login, logout, first-administrator setup, administrator-created accounts for the private group; server-side revocable authentication sessions. One active cooking session per user. Separate settings, encrypted vault and provider calls per user. Reject other users' session IDs, observations, timers, voice and history. Preserve legacy data without silently assigning it to a new account.
2. Recipe library: bundled global recipes remain available to everyone. Administrators manage additional global recipes. Users create/edit/delete personal recipes and copy global recipes to their own library. Cooking saves immutable snapshots. No community moderation or public signup is required.
3. AI recipe maker: accept dish/ingredients, equipment, servings and time budget; use only the user's unlocked AWS connection and selected text/vision model. Validate bounded structured output, show an editable draft and require explicit saving. Generation never starts cooking or publishes globally. Pantry and equipment preferences are optional inputs, never allergy-safety guarantees.
4. Cooking tools: multiple named independent timers with one acknowledgment each; personal cooking history and recipe notes; serving-size adjustment on a new recipe draft; pre-cook ingredient/equipment checklist. Preserve existing manual controls and recipe-independent monitoring.
5. Advisory alerts: classify selected visible concerns separately from step completion. Hazard and possible-emergency severity have separate prominence, evidence and acknowledgment. Never treat two step confirmations as an emergency threshold or automatically advance due to an alert. Show last successful observation time, pending/error/paused/obscured states and stale evidence. No autonomous calls, contacts, appliance control or claims that absence of alerts establishes safety.

## Identity and credentials

Use Werkzeug's supported password hashing, bounded username/password validation and constant-time/generic login failures with throttling. Clear/rotate authentication and CSRF state on login/logout. HTTP-only SameSite cookies; HTTPS and Secure cookies required before remote deployment. User administration requires administrator authorization; public endpoints are limited to the app shell and bounded authentication/bootstrap metadata/actions.

Each user has a separate encrypted vault using the existing passphrase format. Keep login password and vault passphrase separate. Unlock state remains server memory only, starts locked on restart and locks on logout/password reset. No secrets in browser storage, URLs, API responses, logs, recipe drafts or history. Never inherit cloud credentials from process environment for account users. Explicitly authorize the cooking session before upgrading a voice socket; logout/revocation must terminate voice and prevent late observation results from writing state.

Legacy SQLite rows, settings and settings.vault remain on disk and are not exposed to new accounts. Document this preservation boundary; do not decrypt, delete, or automatically claim real legacy data during development. A separate deliberate migration can be specified later.

## Client and API boundaries

Authentication, recipe ownership, vault lookup and cooking authorization live on the server. Keep JSON error envelopes and CSRF/origin checks. The web client renders model/user text as text, supports keyboard and narrow screens, and tears down camera/microphone on logout. A future native client adds secure device credential storage, native capture/audio and notifications; no native implementation, App Store submission or hosting deployment is part of this branch.

## Scope boundaries

Included additions: pantry-aware generation, serving preferences/scaling drafts, multiple named timers, personal history/notes, preparation checklist and monitoring-health display. Household handoff, public registration, email delivery, emergency-service integration and native SwiftUI are later work.

## Verification

Use `.venv/bin/python -m unittest discover -s tests -v` for backend regression and new multi-user scenarios. Run JavaScript syntax checks and isolated WebKit tests under /private/tmp/sous-webkit for authentication, account switching, library/draft ownership, timers, monitoring and voice lifecycle. New AWS calls are mocked with synthetic credentials; no paid inference or physical media devices. Test forged owner IDs, cross-user IDs, logout/revocation, stale in-flight results, locked vaults, restart persistence and existing V1 database migration. Verify the Linux image and disposable sous-verify Compose stack without mutating the normal user's volume. Commit verified slices; no new push/deploy without user instruction.
