Work happens on `feature/v3`. Because merging into `main` deploys to production, merge only verified milestones.

## Shared AWS connection

The user decided this in V3 to cut setup friction when several people demo the app.

- One administrator-managed AWS Bedrock connection, stored in an encrypted vault at `shared/settings.vault` in the data volume, serves every account for camera checks, recipe drafts and voice.
- Only administrators can create, unlock, lock or change the vault, choose the shared model, or list models. Everyone else gets 403 for those actions and sees only whether the connection is ready, plus its region and model. Snapshot interval and voice remain personal preferences.
- The vault starts locked after every restart, including every auto-deploy from `main`. An administrator unlocks it once and it serves everyone until the next restart or an explicit lock. Logout and password changes no longer lock it.
- Bedrock is the only provider. Ollama and the unused OpenAI/Anthropic adapters were removed, and environment cloud credentials are still never used.
- Existing V2 per-account vault files (`users/<id>/settings.vault`) are left on disk and never read. The administrator re-enters the connection once.
- Cost and limits: all usage bills one AWS account, recipe generation stays rate-limited per user, and only one voice stream runs instance-wide.

## Must have

### F1 Kitchen view

This responds to Faria's feedback. The current camera frame is a 16:9 card inside the page, and the voice transcript is capped at 240px. A cook glancing over from a counter about 1–2 m away cannot read either one.

- Add a cooking layout where the camera feed and the conversation fill most of the screen. Use a side-by-side split on landscape tablets and laptops, and a stacked layout on phones.
- Keep the current step, the next timer and the monitoring status visible at distance-readable sizes, using large high-contrast overlays or a strip next to the video.
- Make the transcript a large panel showing the latest exchange in big text. Older turns stay scrollable. Show text that Sous speaks as captions.
- Request a screen Wake Lock while cooking so the screen does not sleep. Offer fullscreen as an option. Both release when the cook ends, the tab is hidden or the user logs out.
- Make controls such as next, back, correct and pause large touch targets that are easy to hit with messy hands. Keyboard and screen-reader behavior must keep working.
- Acceptance: WebKit screenshots at phone portrait, tablet landscape and laptop sizes. The camera takes at least about 60% of the viewport in landscape. All manual controls are still reachable. The existing browser tests pass.

### F2 Real cooking demonstration

This responds to Violet's feedback. The midterm demo used the hand-gesture desk recipe. The final version needs evidence on real food.

- Record at least two real cooks with a fixed overhead or angled camera, for example scrambled eggs plus one recipe with a different structure. Capture step advancement, corrections, timers, voice, a "what do you see?" question (F5) and at least one advisory alert or obstructed view.
- Log what happened during each cook: automatic advances, manual corrections, false advances, missed advances and response latency. Session events and history already hold most of this, so this mainly needs an export or summary view.
- Explicitly connect each feature to cooking support: monitoring reclaims attention, state tracking handles multi-step progress, and voice keeps the cook hands-free.

### F3 Mixed-initiative modes

This is the proposal's core interaction idea. V2 already had the two modes as a per-cook choice, and both still spoke on every step change. V3 makes them actually different.

- **Keep an eye out (monitoring):**
  - Step changes, including automatic ones, appear on screen only.
  - Sous speaks unprompted only for timers (main and named) and advisory camera alerts.
  - The voice companion is told to stay quiet unless the cook talks to it.
- **Talk me through it (assistive):**
  - Sous reads each new step aloud, and when the camera advanced the step it says "That step looks done" first.
  - The voice companion introduces new steps and offers short tips.
- A mode switch in the session bar changes mode mid-cook through the existing `mode` action. It is logged as a session event, so history records it. The voice companion acknowledges the change.
- Every voice context update includes the current mode. Browser speech is used only while the voice companion is off, and no audio is stored.
- Modes change only announcements, never cooking state.
- Tests: voice unit tests cover monitoring-mode quiet step changes, mode-change acknowledgment and assistive narration. Existing session tests cover the `mode` action.

### F4 Evaluation scope

This responds to Violet's IRB comment. Decide early, because it determines what the final report can claim.

- **Option A (recommended for a class project):** the team evaluates the app themselves, as an autobiographical or pilot study, using F2 and F7 data. Report system metrics, not findings about users. No IRB is needed.
- **Option B:** an informal usability check with a few classmates, framed as course feedback and not a study. Confirm with the instructor that this does not require IRB.
- **Option C:** a real user study, which needs IRB approval before recruiting. This is likely not feasible in the remaining time.

### F5 Voice can look at the camera

Today the voice companion cannot see. Its persona says it has no live video, and the `get_cooking_context` tool only returns the latest *stored* camera note along with its age. Nova 2 Sonic takes speech only, not images, so "seeing" has to go through the existing vision pipeline.

- Add a second read-only voice tool, `look_at_camera`. When the cook asks something like "does this look done?" or "what do you see?", the server asks the cook's browser for one fresh frame. It sends that frame with the cook's question to the account's selected vision model and returns a short description to Sonic, which then answers out loud.
- This uses the same credentials, provider adapters and output validation as monitoring snapshots. The frame is used once and not stored, and neither is the description, apart from the ephemeral transcript.
- Update the persona so Sous says "just now I can see…" only for a fresh tool result, and keeps describing older stored notes as earlier observations. Answers stay advisory and cannot confirm doneness or food safety.
- Looking cannot change cooking state: no step advance, no confirmation count and no alert creation. Automatic progression stays with the monitoring loop.
- Bounds:
  - Rate limit per voice session, because every look is a paid vision call.
  - Timeout with a spoken fallback.
  - Fail closed when the camera is off, monitoring is paused or the vault is locked.
  - Only the cook's own browser session can supply the frame.
- Implemented ([voice](voice.md#camera-look)). `tests.test_voice.CameraLookTests` covers the fresh-frame round trip, camera off, unusable frames, provider failure, timeout with stale frame ids, paused guidance, rate limits, invalid arguments and oversized messages, and that state never changes. Sonic and the vision call are mocked, so there are no paid calls. A browser test with a synthetic canvas frame is still to do.

### F6 Create recipes by voice

This is the proposal's reach goal: "use voice-to-text or just input a plan of what they would be cooking, and Sous should be able to create a recipe." V2 can already generate a draft from typed fields, but voice only works during an active cook.

- Add a voice entry point on the Recipes page that does not need a cooking session. The cook describes what they want to make, plus ingredients on hand, equipment, servings and time. Sous asks short follow-up questions for anything missing.
- When the request is complete, Sonic calls a `draft_recipe` tool. That tool uses the existing AI recipe maker (`recipe_ai.py`), with the same validation, rate limits and review warning. The draft opens in the editor.
- Voice never saves, publishes or starts cooking. Saving stays an explicit on-screen action, as in V2.
- Optional: say "change step 3 to…" to revise the open draft before saving.
- Lifecycle follows [voice](voice.md): explicit microphone opt-in, and voice stops on navigation, hidden tab, lock or logout. Audio and transcript stay ephemeral. The single instance-wide voice stream limit still applies.
- Acceptance: unit tests use a mocked tool call and mocked generation. They cover the draft being populated, invalid model output, a locked vault, and a test that voice cannot save. A browser test covers start, stop and the draft appearing.

## Should have

### F7 Offline dataset evaluation

This responds to Violet's suggestion. Replay recorded cooking video through the same recipe and observation pipeline, then score step detection against annotations.

- Candidate dataset: HD-EPIC, which has egocentric kitchen video with recipe, step and nutrition annotations. Before downloading, check its license; the EPIC-KITCHENS family is for non-commercial research only. Also note the domain gap: that footage comes from head-mounted cameras, while Sous expects a fixed counter camera.
- Turn a few annotated recipes into Sous recipe JSON. Sample frames at the configured snapshot interval. Measure step-transition precision, recall and timing error against the annotated step boundaries, comparing at least two models such as Nova Lite and a local qwen3-vl.
- Run this locally, never in production. Keep the dataset and frames out of Git, and budget for paid inference before running it on cloud models.
- Our own F2 recordings can serve as the in-domain test set.

### F8 Explain what Sous believes

This is a trust-calibration feature from the proposal's class connection.

- Show *why* a step advanced or was held back: the matched cue, the model's evidence text and the confirmation count (for example 1 of 2).
- Show uncertainty plainly, distinguishing high, low and stale confidence. The rule that confidence is heuristic still applies.

### F9 Production hardening

The app is now live, so treat it like a live service.

- Back up the SQLite named volume and test a restore.
- Use branch protection on `main` so deploys happen only through reviewed PRs with passing CI.
- Update [STATUS.md](../STATUS.md) and [deployment](deployment.md) to record that production is live; they still say no deployment has occurred.
- Check that Secure cookies, HTTPS-only behavior and the combination of Nginx Basic Auth with app accounts are documented and intended.

## Could have

### F10 Adaptive intervention

This is a proposal reach goal. Use the cook's history, such as how often they correct Sous or turn voice off, to suggest a default mode for F3. Make it a suggestion only, never an automatic change.

### F11 Accessibility pass

Offer a voice-first flow that works without looking at the screen, with every step, timer and alert reachable by voice. Add a high-contrast or large-text preference and support screen-reader announcements for state changes. F1 and F6 cover much of this already.

## Out of scope

Native iOS and TestFlight remain deferred. Also out of scope: public signup, emergency-service calls, appliance control, restaurant compliance, and tracking without any recipe.

## Open decisions

1. Evaluation scope: F4 option A, B or C.
2. Whether to do F7 dataset evaluation, and with which models given the inference cost.
3. Suggested build order: F1 → F3 → F5 → F6 → F2. Recordings come last so they show the final UI, both modes and the camera-aware voice.
4. The voice stream limit is one per instance. With F6, a second user drafting a recipe by voice would block someone else's cooking voice. Decide whether to keep that limit for a few trusted users.
